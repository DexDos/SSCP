# Reconnaissance
The step which is aimed at gaining initial information about versatile architectural details about the target: software, hardware, versions, key stuff and other data which is meant to be converted to a number of **attack vectors**.
## Passive scanning
Scanning the target passively using **Shodan**, DNS-queries and so on. 

In this case, the passive scanning step is rather pointless, since the machine is being hosted locally. 

The only information we need to retrieve is the **IP address**. According to the matter of fact, that we are hosting the machine locally, the optimal way to obtain the target's IP address is scanning the shared subnet with appropriate parameters (the IP range). 
### Locating the target machine's IP
In order to collect the IP range info we need to execute the command `$ ip a` in a shell, which gives us the following:
![Pasted image 20260723190412.png](../../../../Cache/IMGs/Pasted%20image%2020260723190412.png)
The command output gives us information about three net adapters in the OS:
- `lo` — the so-called *loopback*
- `eth0` — the ethernet adapter 
- `docker0` — the virtual adapter for docker subnetting purposes

> **The IP-range we are looking for is:**   `192.168.31.0/24`

>Our IP within a shared subnet: `192.168.31.164`

According to the **subnetting** principles, we have retrieved four octets separated by periods (`.`) in CIDR notation (`/24`). The subnet bits number states that 24 bits of information are referred to the network, whereas the other are left for the subnet usage. Additionally, the first IP address is typically related to the network and the last one for broadcast purposes.

So that we may conclude that the target's machine has received the IP-address within the last octet's range **between 2 and 254**.

Let's scan our subnet in order to receive the target machine's internal IP-address. The utility used: `netdiscover`:
> [!quote]+ The command
> `$ sudo netdiscover -r 192.168.31.0/24`
> 
> ##### The flags used
> - `-r` — specifies the IP <u>range</u> for search
> ---
> More about [netdiscover](netdiscover.md)

The output of the command:
![Pasted image 20260723191840.png](../../../../Cache/IMGs/Pasted%20image%2020260723191840.png)
We have obtained three IP-addresses as candidates for being target's address. Let's break them down:
- `192.168.31.1` — the *1* in the last octet gives us information that this IP is related to the network address and is being monitored by the router.
- `192.168.31.69` — provided that the *MAC Vendor / Hostname* column refers to **Compal**, we may suppose that stated MAC-address is related to the notebook hosting both machines (The target and the attack machines). Compal is a huge corporation manufacturer which ships chips and electronics all over the place. If the last IP doesn't convince us that it belongs to the machine, we'll go back to this option. So far it doesn't seem to be suspicious. 
- `192.168.31.201` — This option has a very specific MAC address. It's MAC starts with the prefix `08:00:27` which directly indicates that it belongs to a **VirtualBox**. Thus we may complete our search, because we have found the needed IP, presumably.

>**Target machine's IP:**    `192.168.31.201`

Let's save the IP within the environment variables for the further usage.
> [!quote]+ The command
>`$ export IP=192.168.31.201`

### Port scanning
Now that we have confirmed the target machine is running and responding in the subnet, we may proceed to explore the target with a slightly higher intensity. Let's discover opened ports of the machine. 
#### Action
The utility used: `nmap`:

> [!quote]+ The command
> `$sudo nmap -sC -sV -v -p-$IP`
> 
> ##### The flags used
> - `-sC` — sets `nmap` to executing ***default set of scripts*** against the target's open ports. Useful for *banner-grabbing*, discovering basic configurations like anonymous access, SSL certificates extraction, NetBIOS, quick and easy vulnerabilities and so on. In addition, this scripts run in a *non-intrusive mode*. 
> - `-sV` — version detection
> - `-v` — increases verbosity of the output so that we retrieve more information during the command execution
> - `-p-` — forces `nmap` to map through the entire pool of the target's ports possible (typically: 1 - 65 535)
> ---
> More about [Nmap](Nmap.md)

> [!note]- rockyou.txt

> Considered to be reliable for common use, it became a standard for CTF platforms as **Try-hack-me**. This rule, so to speak, has gained world wide recognition because of the simple matter of fact that rockyou.txt consists of `14,341,564` unique entries.

>
>**CVSS 3.x: _5.9 MEDIUM_**
> 
> ### Description
> 
>**sshd** in OpenSSH before 7.3, when SHA256 or SHA512 are used for user password hashing, uses BLOWFISH hashing on a static password when the username does not exist, which allows remote attackers **to enumerate users by leveraging the timing difference between responses** when a large password is provided.
> 
> ### Comment
> 
> So basically, this specific CVE allows us to identify the validity of a username depending on timing differences between multiple requests and to mark the one as _contained a valid username_ in case the timing was vastly different from other ones. > ##### Python
> 
> - `import pty;` — Pseudo-terminal utilities. The `pty` module defines operations for handling the pseudo-terminal concept: starting another process and being able to write to and read from its controlling terminal programmatically.
>     
> - `pty.spawn(_argv_[, _master_read_[, _stdin_read_]])` — Spawn a process, and connect its controlling terminal with the current process’s standard io. This is often used to baffle programs which insist on reading from the controlling terminal. It is expected that the process spawned behind the pty will eventually terminate, and when it does _spawn_ will return.
>     
>     We can traverse `_argv_` in two different ways: a cortege (binary and a list of arguments) and a bare binary (a string which is converted to cortege of one element — filepath, leading to the binary).
>     
>     - Python creates a _system call_, using which it spawns two file descriptors: **master** (remains allocated with python) and **slave** (is passed to a child process — binary)
>         
>     - Python calls `os.fork()`, thus creating the child process
>         
>     - `stdin`, `stdout`, and `stderr` are passed to the child process (Python PTY)
>         
>     - PTY calls `os.execv(argv[0], argv)`, thus spawning a shell passed during invocation
>         
>         Consequently, Python Master PTY receives user input to its own `stdin` which is getting passed to Python Slave PTY's `stdin`, which puts input into a shell. When Python Slave PTY pushes its `stdout` to Python Master PTY it passes it to the user shell, completing the loop.
>         
> 
> ##### Why is it needed?
>

And finally let's truncate logging:

1. Find out journal size: `$ journalctl --disk-usage`
    
2. Vacuum the disk volume: `$ journalctl --vacuum-size=__M`
    
3. Truncate the system log file: `$truncate -s 0 /var/log/syslog`
    
4. Truncate the auth log file: `$truncate -s 0 /var/log/auth.log`
    
5. Truncate the kernel log file: `$truncate -s 0 /var/log/kern.log`
    
6. Clean `apt` history if necessary: `sudo apt clean`
    
7. Clean shell history: `history -c && history -w`
    

> **Deleting log files is a very bad idea. No `rm -rf`, truncate them**

There is a ton of stuff to be done more proficiently, but those actions are still gonna cut it for a regular case.
