>[!question]- Why does it work?
>The`UNION` operator is used to combine two or more SQL queries results into a single result. Originally, when we are forwarding an empty query (or the one with *apples*-like results) it forces backend to rely on its own pagination rules to return as much results as it can for a single request. 
>
>Since we are unable to twist the queries around, the first one listed is going to be fetched and get in results. 
>
>However, we are able to mitigate the malicious juice influence by a simple value insertion. This limits the first query results to those matching the criteria. Consequently, the second query results will be the only results fetched.

**Decision reasoning:**

- _The first fix_: attempts to create a kind of a custom filter which is gonna be easily bypassed by formatting characters specified into ASCII (space is `%20`, for example). Thus such an approach is horribly wrong from the beginning.
    
- _The second fix_: attempts to limit the query to options which contain specific words. Such an approach is at least hardly supportable on larger scales. Moreover, it will not cause any security increment as the only thing the hacker needs to do is to determine "green list words" and to use them in a query as we have used the word `whatever`: `.../search?q=apples')) union select username,id,email,password,5,6,7,8,9 from users --`. Not gonna cut it
    
- _The third fix_: the only fix that actually fixes user input direct injection (`${criteria}`). It implements parametrization so that SQL engine handles the query and values separately, entirely protecting from injections of any kind. It is also the only solution which implements a _soft deletion_ handling (`AND deletedAt IS NULL`). This action is also useful had parametrization not been implemented: since we apply `AND` to the result of the first payload (`(name LIKE '%:criteria%' OR description LIKE '%:criteria%')`), fetching a table that does not contain a column `deletedAt` is meant to cause an error. Unfortunately, any common sqli contains `--` comment syntax, which makes the rest of a query useless. But it is still a nice subtle thing to note :D
