# Achievement
Since we know for a fact that Juice Shop uses SQLite we should be able to leverage some sqli techniques in order to group some queries, the one on a website, and the one we need. The technique is described in [[sqli|SQLI]].

To login as an ephemeral user we need to somehow bypass the SQLite users table fetch results. We are capable of doing so by inserting a `selectExpression` into the `FROM` clause so that it is the only thing gets into the scope. This kind of subquery is called a [derived table](https://dev.mysql.com/doc/refman/5.7/en/derived-tables.html):

Here is how to use a subquery in the `FROM` clause, using the example table:
```SQL
INSERT INTO t1 VALUES (1,'1',1.0);
INSERT INTO t1 VALUES (2,'2',2.0);

SELECT sb1,sb2,sb3 
	FROM (SELECT s1 AS sb1, s2 AS sb2, s3*2 AS sb3 FROM t1) AS sb 
	WHERE sb1 > 1;
```

**Why is it needed:**

Here is another example: Suppose that you want to know the average of a set of sums for a grouped table. This does not work:
```sql
SELECT AVG(SUM(column1)) FROM t1 GROUP BY column1;
```

However, this query provides the desired information:
```SQL
SELECT AVG(sum_column1) 
	FROM (SELECT SUM(column1) AS sum_column1 
		FROM t1 GROUP BY column1) AS t1;
```

So that we will inject the `UNION` clause to make SQL unite an empty users table fetch and the desired user row from a derived table. Because of the specifics we will need to mimic all the datatypes and column names, so it would be useful to obtain the `schema.sql` file. `UNION` clause syntax:

```SQL
SELECT ... 
UNION [ALL | DISTINCT] SELECT ... 
[UNION [ALL | DISTINCT] SELECT ...]
```

### Coding challenge
The coding challenge is from *Database Schema*. Firstly we will need to click on the icon representing a coding challenge (`<>`) on the assignment card. Then we are presented with a two step challenge.  

As usually, we are provided with some code snippet to determine the vulnerable solution:

The direct value interpolation, which practically leads to creating a dynamic string, thus concatenating the initial query with a user input, is an unsafe approach by its meaning. We need to use parametrization instead (and apply sanitation because of *Blind SQLI* opportunity).

Let's look at fix options:

Option 1:

![Pasted image 20260807043313.png](../../../../Cache/IMGs/Pasted%20image%2020260807043313.png)

Option 2:

![Pasted image 20260807043336.png](../../../../Cache/IMGs/Pasted%20image%2020260807043336.png)

Option 3:

![Pasted image 20260807043353.png](../../../../Cache/IMGs/Pasted%20image%2020260807043353.png)

**Decision reasoning:**
- *The first option*: seems to be the correct one from the get-go. It replaces interpolation with parametrization so that SQL treats the entire user input as a value, which protects us from corrupting the SQL query logic.
- *The second option*: replaces interpolation with concatenation which effectively does not change a thing. 
- *The third option*: attempts to apply sanitation, which is okay as an additional protection layer. However it could be easily bypassed by somewhat sophisticated ASCII encoding: 
	- `'` sign could be replaced with `CHAR(39)`, `0x27` in HEX 
	- `*` sign could be replaced with `CHAR(42)`, `0x2A` in HEX
	  The exact combination would be eventually picked depending on the database and sanitation complexity, so practically bare rejecting requests containing `'*+="|\/#@-_` etc. symbols is a kind of *Security through obscurity*, but not a real defense layer. 

So that the first option must be the correct one. Let's see if we have evaluated everything correctly:
