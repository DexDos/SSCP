# Achievement
So we need to forge a [[JWT|JWT Token]], which is used by juice shop as a main authorization technology via HTTP header: `Authorization: Bearer ${token}`. 

**JSON Web Token**  consists of three parts:
- `base64url`encoded header
- `base64url` encoded payload
- `base64url` encoded signature (usually SHA-256 is used for `header.payload` hashing) 
These parts are separated by `.` char, so the structure is:
```http
Authorization: Bearer header.payload.signature
```

The header typically contains information about the token type and algorithm:
```json
{
	"typ": "JWT",
	"alg": "RS256"
}
```

There are a few key algorithms 

| Algorithm Family      | JWA identifiers (`alg`)   | Key Type   | Use Case                                         |
| --------------------- | ------------------------- | ---------- | ------------------------------------------------ |
| **HMAC**              | `HS256`, `HS384`, `HS512` | Symmetric  | Internal services, small standalone apps         |
| **RSASSA-PKCS1-v1_5** | `RS256`, `RS384`, `RS512` | Asymmetric | Enterprise Identity Providers (e.g., Auth0)      |
| **RSASSA-PSS**        | `PS256`, `PS384`, `PS512` | Asymmetric | High-security or regulated environments          |
| **ECDSA**             | `ES256`, `ES384`, `ES512` | Asymmetric | Mobile apps, low-bandwidth, high-performance     |
| **EdDSA**             | `Ed25519`, `Ed448`        | Asymmetric | Modern high-speed, highly secure infrastructures |
| **None**              | `none`                    | No Key     | **Insecure**. Local testing only.                |

The two we are interested in are:
- **RS256 (RSA Signature with SHA-256)**: An asymmetric algorithm, which means that there are two keys: one public key and one private key that must be kept secret. Auth0 has the private key used to generate the signature, and the consumer of the JWT retrieves a public key from the metadata endpoints provided by Auth0 and uses it to validate the JWT signature.
- **HS256 (HMAC with SHA-256)**: A symmetric algorithm, which means that there is only one private key that must be kept secret, and it is shared between the two parties. Since the same key is used both to generate the signature and to validate it, care must be taken to ensure that the key is not compromised. This private key (or secret) is created when you register your application (client secret) or API (signing secret) and choose the HS256 signing algorithm.
([Source](https://auth0.com/docs/get-started/applications/signing-algorithms))

The body typically contains some basic information business information (username, role etc.) about the issuer, token subject and so on:
- Issuer (`iss`)
- Subject (`sub`)
- Audience (`aud`)
- Expiration time (`exp`)
- Not before (`nbf`)
- Issued at (`iat`)
- JWT ID (`jti`)

One of the main advantages of JWT is natural REST implementation (facilitates **statelessness** of the servers). It contains signed information about the user which is useful for giant service vendors like Netflix or so, 

But on the flipside, sometimes you need to revoke the token (e.g., when user logs out), which enforces you to create a list of revoked tokens, which effectively makes server **stateful**. If snatched (*hijacjed*) it provides literally no way to detect that. Alternatively, if the server has not set up appropriate algorithms list, it could be forged (or used with `"alg": "None"`).

So JWT tokens need proper management if used. Let's make one.
## Receiving an encryption key
To forge a token we either way need an encryption key. Let's find an endpoint serving that purpose. The first idea came to our mind is a `/.well-known` path.

Well-known endpoints (`/.well-known/`) are standard URL paths defined by [RFC 8615](https://en.wikipedia.org/wiki/Well-known_URI) where websites and servers host machine-readable metadata, policies, and configuration files. They let client programs find service settings automatically without guessing or hardcoding paths.

OpenPGP uses paths like `/.well-known/openpgpkey/` to allow automated clients to discover email encryption keys.

Since the original JWT uses the `RS256` algorithm, which is asymmetric RSA encryption, our only way is to use a symmetric counterpart, which is `HS256` — [[HMAC]] based ( the header and the payload are combined together; `ipad` and `opad` are generated to produce an initial hash and then SHA-256 is used to create a cryptographically secure final hash ). ## Unsigned JWT
To create an unsigned JWT we still have to use the exact same JWT format: `header.payload.signature`.  Since we need an unsigned token specifically we'll need to come up with `header.paylpad.` type of structure. The reason why we need the second dot (`.`) is that regularly JWT parsing methods validate the structure of the token before attempting to parse it into JSON in order not to crash the entire thing. For example:

```ts
export function decodeJWT(jwt: string): object {
	const parts = jwt.split(".");
	if (parts.length !== 3) {
		throw new Error("Invalid JWT");
	}
	let jsonPayload: string;
	try {
		jsonPayload = new TextDecoder().decode(decodeBase64urlIgnorePadding(parts[1]));
	} catch {
		throw new Error("Invalid JWT: Invalid base64url encoding");
	}
	let payload: unknown;
	try {
		payload = JSON.parse(jsonPayload);
	} catch {
		throw new Error("Invalid JWT: Invalid JSON encoding");
	}
	if (typeof payload !== "object" || payload === null) {
		throw new Error("Invalid JWT: Invalid payload");
	}
	return payload as object;
}
```

So we need a ` [ {"type": "JWT", ...}, {"email": "email@example.com", ...}, {} ]` type of structure, where the third JSON object is indeed present, but in an empty state.
